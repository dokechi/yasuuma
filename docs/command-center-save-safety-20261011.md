# 保存処理の段階改修（2026-10-11）

対象: `dokechi/yasuuma`、Supabase `yibtmqsbyodhsudenktm` の `command-center-retro-api`。
基準コード: `ea0df6bf62770490a9e493183917730edaf5891a`。本番API version 28 の全6ソースファイルは、この基準版と一致した。
元の端末checkoutは変更せず、作業フォルダーにコピーして保全した。コピーの未コミット変更は0件。

## 変更と限界

- 投稿用 `saveFpPayload` を常にpayloadの比較付き単一UPDATEにする。読み取りから保存までに他のpayload更新が入ったら409を返す。原稿、承認、実績の各呼び出しへ共通適用する。
- 同じ旧snapshotと同じ保存内容の再送は、既に保存済みの行を返し、再更新しない。これは**完全一致の再送**に限る。API内で生成される時刻が異なるリクエスト、画面を開いた時点からの編集競合、ABA変更、全API共通のリクエストID管理は未対応。
- 仕入れ判定のID、判定値、メモの型と最大長を保存前に検証する。
- 仕入れGETは台帳を書き換えず、既存台帳・候補・判定から同じ得点式で表示用集計を作る。新規候補も表示でき、根拠・メモ・履歴を保持する。閲覧時刻を観測時刻として記録しない。
- 仕入れ先の永続台帳更新は既存の明示的な判定保存経路に残る。本番ledger API version 7 は購入集計と永続台帳の信頼度を読むため、外部処理が直接判定を書き換える場合の永続集計更新は別途調整が必要。
- 判定リセットも、判定削除・候補状態更新の後、成功応答の前に永続評価を再集計する。ledger APIが返す購入注文数1以上の店の古い評価を、UIの`Math.max`が戻してしまう互換性問題を防ぐ。購入件数・金額・メモ・観測時刻を保持する。再集計が失敗したら500を返し、リセット再試行で再集計できる。途中失敗の自動ロールバックではない。
- 仕入れ判定／リセットの複数テーブル更新のトランザクション化は未実施。途中失敗による部分保存の問題は残る。今回の単一行投稿保存とGET非書込の検証を、仕入れ確定全体の原子性保証と混同しない。
- JS/CSS読み込み順、UI、公開URL、認証、投稿・画像保存、利益や売上・入金・ポイントの計算経路を変更しない。Sheetの124候補／189項目は未取得・未移行。Excel／Sheetは操作しない。

## 検証

`node --test scripts/command-center-save-safety.test.mjs` は入力、競合、完全一致再送、保存失敗、削除済み候補、GET非書込、得点上限、観測時刻を検証する。
API経路の競合テストは、両処理が同じ旧snapshotを取得してから保存へ進む同期点を設ける。認証の非同期処理後に偶然逐次保存になる条件と区別する。期待結果は200/409のまま維持した。
リセット回帰は、永続台帳更新と実際のUI再合流関数を合わせて検証する。購入店・未購入店・別候補の判定保持・不正対象拒否・再集計失敗からの再試行を含む。
PostgREST契約の隔離シミュレーターを使う。実DBの並行トランザクション試験ではない。
既存の画像承認テストも実際の保存ガードを呼び、正常承認だけが比較付きUPDATEへ到達することを確認する。

専用ブランチpushとmain向けPRで回帰・追加テスト、新規2モジュールのTypeScript検証を行う。PCへの検証ツール追加インストールは行わない。Nodeの型除去によるAPI経路実行は型検証とは区別する。

## 保全と戻し方

v28の全ソースと設定メタデータは作業フォルダーの `../rollback/retro-v28.json` に保全済み。これはコードの復旧用で、DB・画像バックアップではない。
本番へのDB変更、画像変更・削除、migration、RLS、GRANT/REVOKE、認証設定変更は実施しない。
復旧はv28の同じ6ファイルを同じAPIへ再デプロイする。GitHub側はPR差分をrevertする。DBや画像を戻す操作は伴わない。
